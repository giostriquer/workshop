# Credible product targets

When the reader needs to see how a change will work inside an application,
inspect the actual product or authoritative captures and source styles first.
Use the user's supplied references when live access is unavailable; state
what could not be observed. Do not silently replace a product target with a
generic conceptual card.

## Preserve context

Recreate the surrounding shell, navigation, typography, tokens, spacing,
control conventions, and viewport geometry that make the target recognizable.
Keep the report's visual language separate from the product preview when they
serve different contexts. Use existing product assets where appropriate and
portable; provide accurate fallbacks when they cannot ship with the artifact.

Show credible data density, realistic label lengths, and meaningful states.
For a large-catalog workflow, make scale visible in navigation and selection
behavior instead of drawing three empty cards. Use authorized source data or
clearly identified representative data, respecting the destination's privacy
rules. Never imply sample records are observed user data.

## Make the comparison useful

Keep current and target views on the same scenario and comparable scale. Pick
side-by-side, a toggle, or a sequence according to the difference being shown.
Show enough surrounding workspace to explain where a control belongs. Offer
expansion or a readable full-size view when an embedded preview is too small.

Connect each target to the problem, proposed behavior, constraints, and
acceptance criteria. Relevant states may include editing, validation, cancel,
empty results, pending changes, or approval. Show the states that explain the
decision; decorative controls do not add fidelity.

## Bound the simulation

Label screenshots, reconstructions, proposed designs, and simulations honestly.
State which controls work and what their local actions demonstrate. Unsupported
actions should be clearly illustrative or disabled. Keep prototype edits local
unless the user requested a real integration. A convincing mockup is not proof
of a backend, performance target, saved state, or implemented feature.

Exercise the central flow and its consequential alternatives, including cancel
or validation where shown. Check keyboard focus and navigation; page shortcuts
must not consume input while the reader types in a field. Verify comparison,
expansion, and dismissal controls, including focus return after dialogs close.
