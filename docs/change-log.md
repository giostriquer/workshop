# Release Notes

Release notes for the shipped plugins (`workbench` and `toolkit`) newest
first, one section per released version. Strictly plugin releases: repo-only
work (structure, docs, tooling) lives in `docs/decisions/` and the git log,
not here. **Bounded:** at most 15 release sections: adding one past the cap
deletes the oldest (git history keeps everything). Sections from before the
2026-08-11 plugin split (`reviewers`, pre-split `toolkit`) were dropped in the
2026-08-12 reformat.

## workbench 0.69.0: 2026-11-27

- **Check unwind points under a lock.** `code-quality-review` standard 7 lists each call that can panic or throw between the first write under a lock and its release. Recovering a poisoned lock or catching the error is a claim to verify, never evidence of safety, and a point that leaves invalid state for a later caller is a blocking correctness finding. The review lenses carry the matching question, smell and remedy. ([decision](decisions/code-quality-review.md#standard-7-covers-unwind-points-under-a-lock-2026-11-27))
- **Record a request before a call whose effect can land unseen.** `contract-review` step 3 checks that the exact request is recorded before a call to a durable store, the network or a child process, and settled on every exit, including a panic the caller recovers from. ([decision](decisions/pattern-reviewer-comment-noise.md#the-contract-review-follows-a-call-whose-effect-can-land-without-an-answer-2026-11-27))
- **Ask for landed-effect faults and caller extremes.** `test-quality-review` flags fault fixtures that never land an effect: a panic skips the code that handles a returned error, so it needs its own fault and a test of the next operation. Missing edge cases include the largest value a caller can pass, and the mutation reference says a mutation run cannot find either gap. ([decision](decisions/test-shape-and-mutation-review.md#caller-extremes-and-landed-effect-faults-are-found-by-reading-2026-11-27))
- **Name the fault model of a durability claim.** `epic-orchestration` owner validation adds a claim type for durability, exactly-once and recovery claims. The owner includes an effect that lands before its call fails or panics, checks the next operation after each fault, and does not count a recovered lock or a caught panic as evidence. ([decision](decisions/epic-orchestration.md#durability-claims-name-their-fault-model-2026-11-27))

## workbench 0.68.0: 2026-11-24

- **Write one CI run time section in every PR body.** `file-pr` gains step 11: when the head's checks have finished, and again after every push, the bundled `scripts/ci-run-time.mjs` compares each GitHub Actions job of the PR with the median of its last three successful runs on the base branch and writes `## CI run time`, last in the body above any footer. The table holds the jobs over the limit (more than 10% and more than 20 seconds), the new jobs and the jobs named with `--job`; every job is in a folded block. ([decision](decisions/file-pr.md#one-ci-run-time-section-in-every-pr-body-2026-11-24))
- **Hold the end state for a slower job.** A job over the limit that is also slower than every base run is bold, and its line ends with `_cause and decision not written yet_`, with the steps that grew most under it. The PR is green and mergeable only when that line states the cost removed, the step evidence that it is not from this change, or the user's decision. A job that a base run already matched is marked inside the range and needs no action. With no GitHub Actions job the script exits 3 and the body gets no section; when the read fails the section holds `Not available: <reason>`. ([decision](decisions/file-pr.md#one-ci-run-time-section-in-every-pr-body-2026-11-24))

## workbench 0.67.0: 2026-11-13

- **Run mutest-rs first for Rust.** `test-quality-review` picks one Rust mutation tool per crate from a table. A crate with a `Cargo.toml` runs mutest-rs, which builds once with every mutation compiled in and edits no source file. cargo-mutants runs only when mutest-rs cannot: its install failed or was refused, the crate does not build or pass its baseline under mutest-rs's pinned nightly, or a test longer than 60 seconds reaches the scope. A crate with no manifest that Bazel builds keeps the bundled runner. A completed run never passes its scope to another tool. ([decision](decisions/mutation-scope-and-budget.md#mutest-rs-first-for-rust-2026-11-13))
- **Read a mutest-rs run from its output, not its exit status.** `cargo mutest` exits 0 after a compile error, a failing baseline and undetected mutations alike, so the reference counts a run complete only when the summary line printed and `evaluation.json` exists. Lines that get no mutation (code no selected test reaches within three calls, a function with an `unsafe` block, a bare literal) take hand-applied defects. The Mutation run line reports detected / timed out / crashed / undetected / total per target. ([decision](decisions/mutation-scope-and-budget.md#mutest-rs-first-for-rust-2026-11-13))
- **Queue mutest-rs campaigns.** The slot helper counts `cargo mutest` as a campaign, its mutation listing included, since that type-checks the crate; only `--version` and `--help` take no slot. ([decision](decisions/mutation-scope-and-budget.md#mutest-rs-first-for-rust-2026-11-13))

## workbench 0.66.2: 2026-11-13

- **Stop rerunning flaky tests to green.** `fix-ci` step 5 is now "Rerun or repair?", a table read from the failing log and the branch's diff. Only a failure with no failed test (runner, checkout, install, download, a service the job calls) is rerun as infrastructure. A failed test the branch adds or changes, or whose code it changes, is the branch's fault and is repaired, whatever it does locally or on a rerun. A failed test outside the diff is rerun once and reported by name, with its failure and run link, as a defect that still needs an owner. A rerun is no longer counted beside the two fix attempts. ([decision](decisions/fix-ci.md#a-flaky-test-is-a-fault-not-a-rerun-2026-11-13))

## workbench 0.66.1: 2026-11-11

- **Give the Bazel mutation runner a help.** `rust-mutants-runner.mjs --help` or `-h` prints the usage, every option, the verdicts and the exit codes, and exits 0; the same flags after `--` still go to Bazel. A wrong or missing option exits 1 and says to run with `--help`. The slot helper runs the runner's `--help` at once, as a listing. ([decision](decisions/mutation-scope-and-budget.md#rust-built-by-bazel-with-no-cargo-manifest-2026-11-11))
- **Test the runner's budget guard exactly.** The rule that no mutant starts which the slowest one so far would carry past `--budget` now counts whole milliseconds on a clock its tests replace, so a guard that rounds a mutant's time, moves the boundary by a millisecond or mixes seconds with milliseconds fails a test; the real-time test could not tell a rounded guard apart. That test also no longer assumes mutants take equal time, which failed it on a heavily loaded machine. ([decision](decisions/mutation-scope-and-budget.md#rust-built-by-bazel-with-no-cargo-manifest-2026-11-11))

## workbench 0.66.0: 2026-11-11

- **Mutation-test Rust that Bazel builds with no Cargo manifest.** `test-quality-review` bundles `scripts/rust-mutants-runner.mjs`: cargo-mutants only lists the mutants, from a scratch copy of the crate under a stand-in `Cargo.toml`, and Bazel tests each one in the review's copy, which gets the file restored and its digest checked after every mutant. Only a crate with no `Cargo.toml` up to the repository root, in a repository with Bazel files, takes this route; every crate with a Cargo manifest keeps `cargo mutants --in-place`, even when Bazel also builds it. The run keeps to changed lines (`--base`, or `--in-diff` where the copy has no git), at most 10 mutants and a budget the runner enforces, and the Mutation run line reports `CAUGHT`, `MISSED`, `TIMEOUT`, `UNVIABLE` and the inconclusive outcomes. ([decision](decisions/mutation-scope-and-budget.md#rust-built-by-bazel-with-no-cargo-manifest-2026-11-11))
- **Queue the Bazel runner and clean up after it.** The slot helper counts the runner as a campaign and its `--list` as a listing. The reviewer shuts the copy's Bazel server down when the lane ends, and whoever removes the copy first runs `bazelisk clean --expunge` in it, since Bazel keeps that build tree outside the copy; `receiving-code-review` says so for the session's removal. `test-driven-development` names the runner among the sweeps that belong to the review. ([decision](decisions/mutation-scope-and-budget.md#rust-built-by-bazel-with-no-cargo-manifest-2026-11-11))

## workbench 0.65.0: 2026-11-10

- **Hold every lane PR until the owner has accepted the work.** `epic-orchestration` fixes the delivery order: the lane's completion round ends in a `ready-for-validation` handback with its branch unpushed and no PR, the owner validates that head, and a separate delivery authorization names the accepted revision. A brief, amendment or correction never carries that authorization, and a corrected head is validated before it is authorized. ([decision](decisions/epic-orchestration.md#a-lane-publishes-nothing-before-owner-acceptance-2026-11-10))
- **Check only what was added after acceptance.** At green CI the owner reads each commit added since the accepted revision that is not a clean integration merge and confirms terminal CI, without a second full validation. A PR already open at a head the owner never accepted is validated at once, with a hold line asking the operator not to merge. ([decision](decisions/epic-orchestration.md#a-lane-publishes-nothing-before-owner-acceptance-2026-11-10))
- **Keep the hold on the lane side too.** `epic-implementation` pushes or opens a PR only under a delivery authorization, and answers a dispatch step that orders either before one has arrived with the unpublished handback. The report's `CHECKS` field gains a `delivery` slot: `unpublished (awaiting authorization)`, or the PR, CI and merge state with each commit added since acceptance and its kind. ([decision](decisions/epic-implementation.md#publication-waits-for-acceptance-2026-11-10))

## workbench 0.64.0: 2026-11-09

- **Reconcile lanes every owner turn and drain ready work.** `epic-orchestration` starts each owner turn by comparing every active lane with the ledger, so an unrelayed report is validated and a silent lane is held for the operator. The reply that ends a turn now accounts for every open workset as active, dispatched or held, and carries the closing audit's brief, the closure proposal or a hold when none is open. Hold lines gain `since`, `rechecked` and `operator action` slots, and the slot takes any hold the operator releases. ([decision](decisions/epic-orchestration.md#the-owner-reconciles-lanes-drains-ready-work-and-closes-lanes-out-2026-11-09))
- **Close lanes out and gate closure on follow-ups.** One closeout pointer releases an implementation or audit lane whose delivery merged, whose audit was accepted, or whose remaining work was withdrawn, and names the lane's reporting skill. Closure is proposed only after every follow-up and debt item has the operator's disposition. The label, pointer and return order moved into the entrypoint; journey planning, tracker mapping, delivery detail and the closing audit moved to references. ([decision](decisions/epic-orchestration.md#the-owner-reconciles-lanes-drains-ready-work-and-closes-lanes-out-2026-11-09))
- **Make lane handbacks relayable.** `epic-implementation` ends every final handback with the fenced report block and saves the same block when the contract asks, answers an acknowledge-only dispatch in one line, and puts an approval only the operator can grant in `NEXT STEP` with `operator` as owner instead of opening a question dialog. The lane reads the completion round's inputs from the delivery reference. ([decision](decisions/epic-implementation.md#the-lane-reads-the-completion-rounds-inputs-2026-11-09))
- **Dispatch reviewers with labelled lines.** Each reviewer agent's description now names the lines a parent dispatches it with, and `code-quality-review` no longer asks the parent to paste the diff and file contents. The dispatching session's half of every correction round moved into `receiving-code-review`, which sessions load. ([decision](decisions/code-quality-review.md#the-dispatch-is-pointers-agent-descriptions-name-them-2026-11-09))
- **Send a later delta only to the reviewers whose ground it changes.** A reviewer that passed gets a follow-up when the delta changes production logic or tests (test quality), observable behavior or wiring (contract), or structure beyond its findings' lines (code quality). An applied advisory never returns to the reviewer that raised it. The follow-up message is a fixed set of lines, with optional ones for uncovered mutation scope, forwarded results, a waiver, a hold decision or a user request. ([decision](decisions/bounded-correction-review.md#a-passed-reviewer-sees-a-later-delta-only-when-its-ground-changes-2026-11-09))
- **Open every review report with the verdict.** Code-quality, test-quality, contract and spec reviews now start each round's report with the verdict line, a report without it reads as `ISSUES_FOUND`, and a dispatch's own severity words are mapped in the body. ([decision](decisions/test-shape-and-mutation-review.md#dispatch-lines-and-the-verdict-line-2026-11-09))
- **Let the trimmer commit only on the dispatch's terms.** `comment-trimmer` makes its comment-only commit when the dispatch carries `Commit subject:`, every file it edited was clean and the index holds no one else's staged work; otherwise it reports `Commit: not made` with the reason. It runs the documented formatter over the files it edited and accepts a re-wrap only inside a hunk it trimmed. ([decision](decisions/trim-comments.md#the-trimmer-commits-when-the-dispatch-gives-a-subject-2026-11-09))
- **Define mutation outcomes for restrictions, copies and busy hosts.** A dispatch that limits the mutation lane without citing a waiver is recorded as `blocked: dispatch restriction`, and wait or budget numbers in a dispatch are not applied. The reviewer removes its disposable copy on `PASS` and otherwise reports its path and kind for the dispatching session to remove. A busy host with nothing run stays `blocked: host busy` and gets one follow-up before it goes to the user. The slot helper skips listings and no longer treats `cargo mutants -V` as one. ([decision](decisions/mutation-scope-and-budget.md#restrictions-copies-busy-hosts-and-other-hosts-2026-11-09))
- **Pin code-quality and spec review to Opus 5.5 on Claude Code.** `code-quality-reviewer` and `spec-reviewer` run on `claude-opus-5-5` at `xhigh` on Claude Code whatever the parent runs. Codex and other harnesses keep the parent's model and effort. ([decision](decisions/code-quality-review.md#claude-code-pins-opus-55-at-xhigh-2026-11-09))
- **Bring the model-reference table and notes back into agreement.** `model-reference` corrects reading notes that contradicted the re-graded table, places the `code` axis in the priority order, adds an `effort` column and an ungraded `fable-5.2` row, and defines what a calibrated row records. Escalation now climbs effort before tier: a self-check first, then one effort level below `high`, or the next tier at a lower effort at `high` or above. ([decision](decisions/model-reference.md#table-and-notes-agree-again-effort-is-recorded-escalation-climbs-effort-first-2026-11-09))
- **Give the CI watcher a dispatch block and a way to resume.** `fix-ci` dispatches `ci-watcher` with seven required slots, sizes the deadline from the repository's last successful runs (capped at sixty minutes), and uses literal wait values on Codex. A watch that ended `pending`, or blocked on failed reads, continues once under a `Resume` dispatch with a new deadline; a second read block is reported. A flake rerun gets its own state file. ([decision](decisions/fix-ci.md#stalled-watches-resume-and-dispatches-carry-labelled-inputs-2026-11-09))
- **Name verification at the landing gate and keep evidence across unrelated merges.** `file-pr`'s gate now names `verification-before-completion` and its three operative rules. A clean merge of target commits keeps local check evidence only when no incoming path is one the branch changes, is read by an affected check, or depends on what the branch changes; anything else reruns the checks. ([decision](decisions/file-pr.md#unaffected-clean-merges-keep-their-check-evidence-2026-11-09))
- **Keep the orientation out of dispatched subagents.** `using-workbench`'s description excludes a subagent dispatched for a specific task, routes a written spec or plan to `spec-reviewer`, and states the disposable-checkout rule for pre-fix comparisons in its verification summary. ([decision](decisions/skill-descriptions-state-when-not-what.md#using-workbenchs-description-excludes-dispatched-subagents-2026-11-09))
- **Check for unwritable directories before removing a worktree.** `workspace-cleanup` runs a check for directories the user cannot write before a non-force `git worktree remove`, holds the entry on any hit and asks for the permission change, since Git drops the registration even when it cannot delete the files. ([decision](decisions/workspace-cleanup.md#read-only-directories-are-checked-before-worktree-removal-2026-11-09))
- **Ask open questions before offering options.** `brainstorming` asks what the user wants the thing for as a plain open question, says what each answer would change, and drops weak approaches before proposing two or three, or one with the reason the others do not fit. ([decision](decisions/skill-wording-hardening.md#brainstorming-takes-three-question-techniques-from-upstream-v702-2026-11-09))

([decision](decisions/claim-check.md#the-verdict-buckets-are-listed-in-the-spec-2026-11-09))
