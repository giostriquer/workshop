# fix-ci

[Canonical skill](../../plugins/workbench/skills/fix-ci/SKILL.md)

## What it does

`fix-ci` sees the current branch's CI through to a verdict and fixes what
breaks: it pulls the failing log, decides rerun or repair, fixes in-session,
pushes, and re-watches. It is the invocable form of "CI is failing, take a
look."

The fix happens in your session, with the context of the commits that broke the
build. The waiting happens in the read-only `ci-watcher` agent, which never
fixes, reruns, commits or pushes.

Fixes land as ordinary commits: no force-push, amend or history rewrite. It
fixes only the cause of the red check and reports unrelated failures and
dirty-tree changes rather than sweeping them in. It never deletes, skips or
weakens a check. It stops after **two fix attempts per failing cause**.

## When to reach for it

When the branch's CI is red and should be fixed, or right after a push when the
checks should be seen through to green.

| The problem | The skill |
| --- | --- |
| CI is red on this branch and should be fixed | `fix-ci` |
| You want a pass/fail verdict and nothing edited | the `ci-watcher` agent |
| A finished branch should become a PR and be tended to green | `file-pr` (it runs this loop) |
| A persistent or unclear bug in the code itself | `systematic-debugging` |
| A failing check is really a question about intended behavior | `fix-ci` reports it as a decision for you |

## The loop

1. **Resolve the target.** Find the branch's PR and its target repository and
   branch, or its push-triggered runs if it has no PR. Pin the target SHA with
   `git rev-parse HEAD`, confirm it matches the remote head, and identify the
   required checks. No branch, no CI or no access
   gets a precise report.
2. **Dispatch one watcher** for that SHA: a separate `ci-watcher`, even when
   your session is idle, with a labelled block whose seven slots are all
   filled: `Runner`, `Repo`, `PR` (or `Branch`), `SHA`, `State file` (named by
   the SHA, and by run and attempt for a step 5 rerun), `Deadline` and `Expected
   checks`. The deadline comes from one read of the repository's last
   successful runs: the longest workflow's run time, plus half again, capped at
   sixty minutes; ten minutes only when there is no run to read. On
   Claude Code it is dispatched by name with no model, since its agent file
   pins the model; on Muse, by its approved scoped definition
   (`workbench/ci-watcher`) with no model. Codex registers no agents, so the spawn uses the arguments
   the agent file's Dispatch line names, and its message pastes that file's
   body ahead of the inputs.
   It invokes `scripts/watch-ci.mjs` from the loaded `fix-ci` skill, using
   Node 18+ and authenticated `gh`. Polling, deadlines, rerun identity and
   verdicts live in that command, rather than code generated by each agent.
   On supported Claude Code hosts, background command completion wakes the
   watcher after it yields; its final handback wakes the parent. Older hosts use
   bounded foreground slices. On Codex the process stays running between tool
   waits. The
   parent waits through the host mechanism: on Codex, `wait_agent` at
   `timeout_ms: 600000`, lowered only after a host error that names a limit.
   It returns at the
   **first failed check or job on the pinned revision**, including failures not
   listed as required, at a **merge conflict**, or the moment the PR **merges
   or closes**. Its report lists the checks still pending. For a conflicted PR,
   the branch's faults among the listed failures are fixed first, nothing is
   rerun, and synchronization (step 8) resolves the conflict without using a
   fix attempt. The runner's `passed` verdict describes reported checks on a PR
   GitHub reports mergeable. Green also requires every known required check to pass on
   the pinned SHA; unspecified coverage, missing, cancelled or superseded
   checks are not green. A watch that ends `pending` at its deadline, or
   `blocked` by failed reads, is continued: a `Resume` dispatch names the
   returned state file and a new deadline, and the runner keeps the saved
   target and expected checks.
3. **The parent collects evidence after the watcher returns.** `gh run view <run-id> --log-failed`, then read the
   failing step's output. For an external check, surface the link; if the cause
   isn't reachable from the repo, report rather than guess.
4. **Diagnose in repo context.** The branch's own recent commits are the prime
   suspects, ahead of infrastructure.
5. **Rerun or repair?** The failing log and the branch's diff decide:

   | The log shows | The diff | Then |
   |---|---|---|
   | No failed test: the runner died, or checkout, install, a download or a service the job calls failed | anything | Infrastructure failure: rerun |
   | A failed or timed-out test | adds or changes that test, or code it runs | The branch's fault: it is repaired |
   | A failed or timed-out test | touches neither | Another owner's broken test: rerun, and reported |

   A flaky test is a broken test. Passing locally, on an earlier head or on a
   rerun does not clear the branch's own test: the loop finds what differs
   between runs and fixes that. A rerun is one `gh run rerun <run-id> --failed`
   and one more watcher for the head, given the run and the attempt that
   failed. It waits for the rerun's new attempt, so the old failure cannot end
   it, then watches every check on the head. On Codex that watcher is a fresh
   spawn.
6. **Reproduce locally when feasible.** Run the focused failing case before and
   after the fix, plus mandatory local gates; full suites run in PR CI.
7. **Fix in-session**, addressing only the cause. After completed review, a
   bounded CI repair goes through synchronization and focused verification to
   push and re-watch, without another review or mutation round for the repair
   alone. Integration changes receive affected review when they invalidate
   prior coverage. Open reviewer findings
   remain open. A fix that requires new scope or a different design is reported
   as a decision before the repair expands; user and repository requirements
   still apply.
8. **Synchronize before every repair push**, preserving unrelated dirty work and
   committing only the fix's files. Refresh the PR's state, head and actual target;
   merged or closed ends this loop with unpushed work preserved. Pull the remote
   feature head, fetch the current target from its repository, and merge missing
   commits even without conflicts. Resolve mechanical conflicts and semantic
   collisions settled by the accepted requirements, then validate the combined
   result and refresh the diff, PR text and any invalidated review coverage.
   Read the old head's checks once and fold any new in-scope failure into the fix.
   Immediately before pushing, refresh and fetch the target again and verify its
   tip is in HEAD. If it changed or has missing commits, synchronize and validate
   again. A clean merge keeps the existing check evidence when the incoming
   target paths, with renames expanded, include no path the branch changes, no
   path an affected check reads and no path that imports, builds from or tests
   one the branch changes, directly or through other modules; a path that
   cannot be placed or bounded counts as read. Synchronization
   has no retry cap; remote-head push rejections also return to
   synchronization and validation. These rounds neither consume nor
   reset CI fix attempts. An unresolved merge or failed fetch leaves the push
   pending. Branch-only CI pulls its upstream without inventing a PR target.
   No-commit or no-push instructions hold; the report names the remaining step.
9. **Re-watch** with a new watcher for the new head. A different check failing
   there is a new cause with its own two attempts; the same check failing after
   its second fix ends the loop.

## Common questions

**What stops duplicate watches or stale runner results?** Every invocation and
result identifies protocol 2. An older runner or saved state produces a version
gap instead of inheriting newer mergeability guarantees. A per-user registry
shares ownership for the same GitHub host, repository, PR or branch, SHA and rerun attempt,
even across different state filenames. A duplicate gets the original state
location or saved terminal result, with its observation time. Expected-check
sets must match; a saved result is not a fresh readiness check. A saved
`pending` or read-error `blocked` result is the one kind that continues, and
only through a `Resume` dispatch with a new deadline. Resuming under
a changed `GH_HOST` is blocked so the saved target cannot silently change.

**Does it still poll GitHub?** Yes, every thirty seconds. The runner reuses
completed job details only while current metadata confirms the same run and
attempt, and still reads running jobs for early failures. Rate limiting pauses
reads within the original deadline. The handback contains compact verdict
facts; full check details stay in the state file.

**Will it handle conflicts itself?** Yes. It resolves mechanical conflicts and
semantic collisions whose result follows from governing requirements or
decisions, verifies the result, and continues. It asks only when resolution
needs a new scope, product, policy or authority decision. Each push includes a
fresh sync of the PR's actual target, regardless of whether GitHub reports it
as mergeable.

**Why did the watcher return `conflicted` before CI finished?** A PR with merge
conflicts cannot merge whatever its checks say, and GitHub starts no
`pull_request` workflows on it, so the watch would only run out its window. The
watcher reads mergeability on every poll and returns at the first conflict. If
GitHub has not finished computing mergeability, green checks wait for it; a
watch that ends while waiting reports a pending `GitHub mergeability` row.

**It re-ran the job instead of fixing anything.** A rerun is for a failure
the branch did not cause: the infrastructure failed before any test did, or
the failed test and the code it runs are outside the branch's diff. It fires
once. If the rerun comes back red, the loop treats it as a fault.

**My new test failed once in CI and passes locally. Why no rerun?** A test
that passes on some runs and fails on others is broken, and a rerun to green
would ship it. When the branch adds or changes the test, or code it runs, the
loop reproduces the failure under the CI job's conditions and fixes what
differs between runs (timing, ordering, shared state, clock, randomness).

**It reran someone else's flaky test. Is that test now forgotten?** No. The
report names the test, its failure and the run link as a defect that still
needs an owner.

**It stopped after two attempts and left CI red.** That is the cap. Instead of a
third attempt you get the diagnosis, the failing-log excerpt or check link, and a
recommended next step.

**Do repeated target updates use those attempts?** No. The limit counts fixes
for a failing CI cause. Target and remote-head synchronization continues as
needed, with validation before each push, and neither consumes nor resets the
CI attempt count.

**Why won't it just skip the flaky test?** A red check that encodes an
intended-behavior question is reported as a decision for you, not worked around.

**Why did it return while other checks were still running?** Any failed check
or job on the pinned revision ends the watcher's turn, even if it is not listed
as required or an aggregate gate is still pending. The report uses the observed
snapshot and available links. Log fetching, branch-rule checks, diagnosis, and
repair decisions happen in the parent after that handback. Missing logs do not
delay notification. Checks still running when a fix is pushed rerun on the new
head anyway.

**My branch has no PR.** It works the branch's push-triggered runs, pinned to the
target commit. ([decision](../decisions/fix-ci.md))

**Can I keep working while it waits?** Yes. The watcher runs separately; your
session picks up its report and owns the fix. If no watcher can be dispatched, it
reports the monitoring gap rather than polling in your session.

**Why not a Monitor or a background loop in my own session?** *(Claude Code
only.)* Every turn your session spends is billed at its own model, and a Fable
or Astra session is the expensive one; a Monitor also wakes you once per output
line. The watcher's Sonnet 5.5 turns cost less, so the loop lives there. After
dispatching, end your turn: the harness re-invokes you with the watcher's report,
so you do not poll `gh`, arm a Monitor, or read the watcher's output file in the
meantime.

**How does the watcher wait on Claude Code?** On supported persistent hosts,
it starts background Bash and yields until command completion re-invokes it.
A background command is not bound by the ten-minute foreground maximum, so its
timeout is the whole remaining window plus sixty seconds and the watch runs as
one command. It slices only after the host rejects that timeout with an error
naming a limit.
An interim yield notice may reach your session; that is not a verdict, so yield
again until the final handback. A one-shot CLI that exits on the initial result,
or a host without completion notifications, uses foreground slices below its
actual call ceiling instead. The one-shot parent also dispatches the watcher
in the foreground so it stays alive until the verdict.

**On Codex, my session sits in `wait_agent`.** That is the wait. A finished
watcher does not wake your session, so it waits ten minutes at a time
(`timeout_ms: 600000`) until the final answer, using a shorter wait only after
the host returns an error that names a limit.
Host-required status updates do not require another GitHub poll.

**On Codex, why does the spawn message carry the whole watcher contract?**
Codex registers no plugin agents, and a watcher told only where its file is
tends to read this skill instead, with its fix, commit and push steps. The
pasted contract keeps the watcher read-only. A follow-up to that watcher
carries only a new pinned head; the fix stays in your session.
([decision](../decisions/plugin-surfaces.md))

**The watcher came back with checks still pending.** Its watch window is
bounded by the deadline your session sized from the repository's recent runs.
Pending is reported as pending, never as green. Your session then dispatches a
`Resume` with the returned state file and a new deadline, which continues the
same watch. If the resumed watch returns pending again with the same checks
still unsettled, it reports a stalled run with the check links instead of
resuming again.

**The watcher came back `blocked`.** Four polls in a row could not read the PR,
as when `gh` auth has expired or the network is down. The report carries the
last `gh` error; fix access, confirm it with `gh auth status`, then dispatch a
`Resume` with the returned state file and a new deadline. If the resumed watch
blocks on reads again, it is reported instead of resumed again. A
`blocked` that names cancelled checks or no passing check is a verdict and is
reported as is.

**The plugin updated while my session was running and the runner path is
gone.** The session passes the installed version's runner, taken from the
host's plugin record (`claude plugin list --json` or `codex plugin list
--json`). A watcher handed a missing path resolves it the same way and names
the path it used. Neither searches the cache for another version.

**The PR merged while the watcher was running.** It returns right then with
`merged`, the merge time and the checks' state at that moment; it does not wait
for checks still running on the merged head. A closed PR returns `closed` the
same way, and the loop ends.

**My unrelated changes didn't get committed.** Correct: it stages only files the
fix touched and reports the rest.

**GitHub refused the rerun, or the verdict looks wrong.** The session you are
working in decides the next step, such as waiting for the run to finish before
rerunning, and tells you plainly what happened and what it chose.

**Non-GitHub CI?** It assumes `gh`.

## It's working if

- The diagnosis quotes the failing step's output. **Negative signal:** a
  diagnosis offered before any log was pulled.
- Each attempt reports what failed, the root cause, and what changed (files and
  commit).
- The final report names the verdict, target SHA, expected checks, watcher model,
  and PR or run link.
- The fix commit touches only what the failure required.
- A detected failure reaches the parent without waiting for unrelated pending checks.
- Watcher waits follow the host's limits and status-update requirements; the
  parent does not duplicate GitHub polling.
- **Negative signal:** a force-push, an amended commit, a skipped test, a third
  attempt on one cause, a second watcher on the same head other than the
  one after a step 5 rerun or a `Resume` of a pending or read-blocked watch, a
  rerun of a test the branch added or changed, a rerun with no line in the
  report, a
  dispatch with an unfilled slot, or a Codex watcher handed anything but a
  head to watch.

## Where it fits

`fix-ci` tends the checks in the landing stage, after `file-pr`, a merge, or a
push. `file-pr` runs this loop rather than duplicating it. The `ci-watcher` agent
is its read-only watch half.
