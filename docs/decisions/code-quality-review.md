# code-quality-review: decisions in force

Rationale for the `code-quality-review` skill and its `code-quality-reviewer` agent, both shipped by the workbench plugin; superseded choices are omitted, and git history keeps the originals.

## A strict, structure-first review skill (2026-06-29)

The flow had reviewers for specs, pattern conformance and tests, but nothing aimed at a diff that works and passes tests while leaving the codebase messier: a file crossing 1000 lines, a special case bolted onto an unrelated flow, feature logic in a shared path, an abstraction that buys nothing. The skill fills that gap with a deep-audit baseline prompt and eight standards, all biased toward deleting complexity through a "code judo" reframe rather than rearranging it. It stays system-agnostic, with no product, framework, path or ticket names, and its one number, the 1000-line threshold, starts a decomposition conversation rather than acting as a mechanical cap. Its target is the maintainability of a bounded change, so it complements `pattern-reviewer`'s conformance check instead of replacing it, and it is not a whole-repo audit. The source is Cursor's MIT-licensed `thermo-nuclear-code-quality-review` skill from the `thermos` plugin in [cursor/plugins](https://github.com/cursor/plugins), whose text the skill still keeps nearly word for word. The name is neutral: the source's "thermo-nuclear" branding was dropped from both skill and agent, and the skill is model-invocable.

## The skill is the rubric; the agent applies it (2026-06-29)

The implementation-review loop always named a code-quality stage ahead of pattern review, but no agent filled it, so every adopting project had to supply its own. `code-quality-reviewer`, adapted from the agent of the same rubric in Cursor's MIT-licensed `cursor-team-kit` plugin, fills it by loading the `code-quality-review` skill as its complete rubric, reading the bundled SKILL.md directly on hosts that do not auto-load skills, and falling back to a harsh maintainability audit in the same spirit only when the skill is unavailable. One rubric in one place means the agent carries no second copy to drift. The agent is host-agnostic: it reviews the `### Git / diff output` and `### Changed file contents` sections a parent supplies, or gathers the diff against the base itself, so it works both as a dispatched stage and standalone. It is review-only; the implementer owns every fix.

## The review is default-on at completion (2026-08-12)

Sessions finished, verified and went straight to landing, because the flow text called `verification-before-completion` the only always-on piece and framed every skill as a default rather than a gate. The review is now required once the agreed work is complete, with exactly two exits: the user explicitly declines, or the repo's own process supersedes it. A small diff, a confident implementation, a clean-looking change, time pressure, or the session's own sense that this one looks fine do not qualify, because that judgment is exactly what an adversarial pass exists to distrust. The description carries the mandate in one word, "required", and the body carries the exits and non-reasons, since policy in the description taxes every session to serve the few where the skill fires; the description also names "adversarial", the word the rest of the flow uses for this pass. Being mandatory does not widen the review: it never runs mid-implementation, and out-of-scope findings become follow-ups rather than growing the diff.

## The review is dispatched, never self-served (2026-08-19)

Sessions reaching the gate ran the rubric over their own diff and reported that as the review, and nothing in the text told them otherwise. The implementing context holds every justification behind the code, so its structure reads as inevitable and the code-judo move the rubric hunts for is exactly what that context cannot see; a self-served pass returns "nothing blocking" on diffs a fresh reviewer takes apart. The review therefore runs in a fresh context handed the diff and the changed files, normally the `code-quality-reviewer` agent, and where the host has no subagent mechanism the diff goes to a fresh session and the report names that route. An author's pass over their own work is reported as what it is, never as the gate. The requirement follows from the review being adversarial, not from a general preference for dispatch, so it does not extend to `pattern-reviewer`; it lives in the skill text alone, with no hook or dispatcher.

## The reviewer gets the accepted scope (2026-09-24)

The rubric labels findings in scope, advisory or follow-up against "the accepted work's boundary: the ticket, plan, or agreed change under review", but the dispatch handed the reviewer only `### Git / diff output` and `### Changed file contents`, so it had to infer the boundary from the code it was judging. The dispatch now carries an `### Accepted scope` section: the ticket, plan or agreed change stated as the ask, never the author's account of the code, the way pstack's `interrogate` (cursor/plugins, MIT) states the intent before its reviewers run. The section sets where in-scope ends and does not limit what the reviewer reads or traces. An assessment that arrives with it is not the reviewer's to adopt, the stance `test-quality-review` takes toward its caller. A reviewer given no scope takes it from the PR description, the commits or the ticket they reference, and says which scope it used.

## The 1k-line rule has one reading (2026-09-24)

Standard 1 still ended "Only waive this if there is a compelling structural reason and the resulting file is still clearly organized". That line is left over from the presumptive-blocker wording the 0.37.0 pass replaced, and it reads as blocking by default, while the scope boundary and the approval bar say file length alone never establishes a blocker. The bullet now says the crossing alone is advisory and blocks only on a demonstrated maintainability consequence, and the usage page's "hard cap" answer matches. The other mentions (the review question, the flag list, the example phrase, the priority list, the approval bar, and the agent's fallback, which its Work section already qualifies) carry the current reading and are unchanged. The current wording's reviewers already labeled a 1k crossing advisory in the probe below, so this corrects a contradiction in the source rather than a measured failure.

## The review carries the comment trim (2026-09-24)

`using-workbench` defines the required round as "code-quality-review + comment trim, per repo rules", but the rubric never mentioned comments, `file-pr`'s gate names only the two reviews, and the one comment check lived in `pattern-reviewer`, which no gate dispatches. Standard 8 gives the trim to this review, as findings the implementer acts on: comments the repository's rules say to remove, a lint or type suppression that silences a rule protecting correctness or safety, and a constraint comment ("do not remove") that a test, type or lint rule could enforce. The checks come from pstack's `no-comments` skill and `comment-sicko` agent (cursor/plugins, MIT). Their persona, their default of deleting every comment, and their direct edits were left out: this reviewer is review-only, and the repository's rules decide which comments go.

That left two reviewers owning comments with different defaults: `pattern-reviewer` flags restating comments with or without a repository rule, and standard 8 flags only what a rule covers. Each now names the other's share. Standard 8 says a comment that only restates the code, with no rule against it, is `pattern-reviewer`'s built-in check wherever that agent runs, and this review does not flag it; `pattern-reviewer` says the rest of the trim (rule-covered comments, suppressions, enforceable constraint comments) is standard 8's. In a plan-only probe, two fresh reviewers per arm judged a diff with narrating comments and no comment rule, a `no-floating-promises` suppression over a call whose rejection crashes the service, and a "keep in sync with the docs" comment. Both arms flagged the suppression with its fix 2 of 2, named a test to enforce the sync comment 2 of 2, and left the narrating comments unflagged 2 of 2; this wording's reviewers named `pattern-reviewer` as their owner 2 of 2, the first draft's 0 of 2. The change settles ownership rather than behavior, and two reps per arm is bounded regression evidence.

## The reviewer runs on the parent's model without the author's history (2026-09-24)

The agent file already set `model: inherit`, but Codex registers no plugin agents, and Codex's `spawn_agent` forks the parent's whole history unless `fork_turns` says otherwise. A 30-day audit of Codex sessions counted 96 of 203 reviewer spawns forking the author's full history. A forked reviewer inherits the justifications that make the author's structure read as inevitable, the blindness this dispatched review exists to avoid. The operator kept the reviewer on the parent's model on both hosts, so the dispatch lines now read: on Claude Code, pass no model; on Codex, `spawn_agent` with `fork_turns: "none"` and no `model` or `reasoning_effort`, which then inherit the parent's.

The workbench LICENSE and the root README now credit the Cursor sources named in the first two sections (`Copyright (c) 2026 Cursor`, MIT) beside the superpowers notice.

Plan-only probes checked these changes, with fresh Opus contexts per arm, one arm reading the current skill and agent files and one this wording. In the dispatch probe, a Codex parent (with a Claude Code variant) about to file a ticket's PR wrote its review spawns, while holding the view that its change was clean; two reps per arm. In the review probe, the reviewer judged a synthetic diff that crossed 1,000 lines in a well-sectioned file, added narrating comments and a commented-out stub against a quoted repo comment rule, suppressed `no-floating-promises` over an analytics call that rejects, guarded the column order with an "IMPORTANT: do not remove or reorder" comment, and sat beside a pre-existing date bug; the dispatch also carried the author's "this came out clean" note. Three reps per arm.
